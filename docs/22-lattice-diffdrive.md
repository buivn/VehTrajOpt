# 22 — State-lattice path generation for diff-drive

Doc 20's matrix marked lattice as "Adapt" for M1 (plain lattice, not Hybrid A\*'s
bounded-turning-radius variant — M1 has no minimum turning radius). Doc 21 ruled out
DWA; this is the actual first generation-method pipeline for M1. Design only, as
usual — theory + method selection + design, no code yet.

---

## 1. General idea / theoretical aspect

A **state lattice** is a discretized *search graph* whose edges are not arbitrary
cell-to-cell hops but pre-computed **motion primitives**: short trajectories
generated by simulating the robot's own motion model forward from a canonical pose
for a fixed duration. Planning then becomes a graph search (same A\* algorithm) over
this primitive graph instead of over raw grid connectivity. Primitives are generated
**once**, from pose `(0,0,0)`, then reused everywhere on the lattice by rotating to
each node's discrete heading and translating to its cell — this only works because
the robot's dynamics are time-invariant and homogeneous in `(x,y)` (a primitive
executed from any pose looks the same, just rotated/translated).

Concretely vs. the existing planner: `astar.py`'s search state is `(row, col)`
only — a plain position graph
([astar.py:107](../ros2_ws/src/vto_planning/vto_planning/astar.py#L107)), and its
edges are 8 fixed directions at 45° increments regardless of what the robot is
([astar.py:23-24](../ros2_ws/src/vto_planning/vto_planning/astar.py#L23-L24)). A
lattice adds **heading** to the search state — `(row, col, heading_index)` — and
replaces the fixed 8-move table with a small library of primitives that reflect how
the robot actually moves (straight runs, constant-curvature arcs, in-place pivots).
Still a *global* planner producing a path, same pipeline stage as A\* today.

---

## 2. Method selection — why lattice, and an honest caveat about what it buys M1

**The caveat first, because it changes the justification:** for a genuinely
non-holonomic robot (M2 car-like, bounded turning radius, can't pivot), a
lattice/Hybrid A\* is about **feasibility** — plain grid A\* can return a path the
robot physically cannot drive. M1 is different: a diff-drive robot can pivot in
place, so it can *always* execute an 8-connected grid path (drive a leg, pivot,
drive the next leg) — doc 10 already leans on exactly this (turn-in-place fallback
in Pure Pursuit). So for M1, lattice is **not** buying feasibility that wasn't
already there.

**What it does buy for M1: path *quality*.** The current 8-connected path is a
jagged sequence of 45°-multiple segments — every corner is a full stop-pivot-drive
event. A lattice with primitives that include gentle constant-curvature arcs (not
just straight + 45° pivots) produces a path with fewer stop-and-pivot events and
lower curvature, which matters concretely against the metrics in doc 20 §3:
`time_to_goal`, `dw_rms` (angular-rate smoothness), and doc 10's curvature-slowdown
term (a smoother reference path triggers that slowdown less often). This reframes
the comparison from doc 20 as "does it work" (M1: already works) to "how much
better does the *execution* get" — a more honest and more interesting question for
M1 than the feasibility story that applies to M2/M3.

**Why not just tune A\*'s existing clearance/inflation more instead:** that only
shapes *where* the path goes (center of corridor vs. hug one side), not *how it
moves through* a corner — clearance weighting can't turn a 45°-jump corner into a
smooth arc, because the move set is still fixed 8 directions.

**Why not Hybrid A\*/Dubins-RS proper:** already ruled out for M1 in doc 20 §1 (both
assume a bounded turning radius M1 doesn't have — would be planning for a stricter
robot than the real one, same mistake doc 20 flagged for Dubins on M1).

**Why not sampling (`src/GP` `MPTreePlanner`) instead:** still needs a new,
simpler `MotionEqs` subclass for M1's first-order kinematics before it's usable
here — real work, separate step, not blocked by this doc.

## 3. Coding — design

### Where it lives, and what's reused vs. new
Same package as A\*, same core/node split
(`vto_planning/astar.py` /
`astar_planner_node.py`
([astar_planner_node.py:63-65](../ros2_ws/src/vto_planning/vto_planning/astar_planner_node.py#L63-L65))):

- **`vto_planning/lattice.py`** — new core module, framework-free, unit-testable
  (`test/test_lattice.py`, mirrors `test_astar.py`).
- **`vto_planning/lattice_planner_node.py`** — new ROS adapter.

**Interface is a deliberate drop-in match:** subscribe `/map` (OccupancyGrid),
`/goal_pose` (PoseStamped), publish `/plan` (Path) — identical topics to
`AStarPlanner` ([astar_planner_node.py:63-65](../ros2_ws/src/vto_planning/vto_planning/astar_planner_node.py#L63-L65)).
Swapping which planner node runs in `maze_astar.launch.py` is then the only change
needed to compare pipelines — Pure Pursuit/MPC/MPPI and `vto_bench` need **zero**
changes, which is exactly the "generator paired with an existing tracker" shape
doc 21 §5 said DWA should have had.

**Reuse, don't reimplement, the grid utilities `astar.py` already has:**
`is_free`, `clearance_field`, `inflate_obstacles`
([astar.py:26-95](../ros2_ws/src/vto_planning/vto_planning/astar.py#L26-L95)) —
obstacle representation doesn't change, only the search state and edge set do.
`_reconstruct`'s parent-link walk-back also carries over unchanged (works on any
hashable state tuple, `(r,c,h)` included).

### Data structures and why

- **Search state: `(row, col, heading_index)`, not `(row, col)`.** Same
  `heapq` open-set + `g_score`/`came_from` dicts as `astar()`
  ([astar.py:142-146](../ros2_ws/src/vto_planning/vto_planning/astar.py#L142-L146)),
  just a 3-tuple key instead of 2-tuple — the algorithm skeleton doesn't change,
  only what a "state" is. `heading_index` discretized to e.g. 16 bins (22.5°
  resolution) so primitives compose exactly onto integer grid+heading cells with no
  continuous-state interpolation needed during search.
- **Primitive table — a small precomputed list, generated once at node startup, not
  per search.** Each primitive is a tuple `(dcell_row, dcell_col, dheading_index,
  cost, poses)`: `poses` is the closed-form sampled `(x,y,θ)` trace of the
  primitive (straight line, or constant-curvature arc — same closed-form arc math
  doc 21 §3 used for DWA rollouts, reused here for primitive generation instead of
  DWA scoring). Generated once for heading 0, then a lookup table `heading_index ->
  [primitives rotated to that heading]` is built once at startup by rotation — 16
  headings × ~5-7 primitives ≈ 100 entries, trivial memory, O(1) lookup per search
  expansion. **Why precompute instead of generating on the fly:** the whole point of
  a lattice is that primitives are reusable by symmetry; recomputing the same arc
  math on every node expansion would be pure waste.
- **Primitive set (draft, to confirm below):** straight-ahead, arcs at 2-3 curvature
  levels turning left/right, and in-place pivot. The curvature levels should reuse
  whatever bound doc 10's *deferred* "curvature-regulated speed" work would have
  used — same underlying limit, one fewer number to invent independently.
- **Collision-checking a primitive — new logic, not in `astar.py`.** Vanilla A\*
  only checks the destination cell (plus, for diagonals, the two shared
  orthogonals) ([astar.py:159-164](../ros2_ws/src/vto_planning/vto_planning/astar.py#L159-L164)).
  A curved primitive can clip a wall mid-arc without either endpoint being
  occupied, so validity must check `is_free` at every sampled pose along the
  primitive's `poses` trace, not just the endpoint.

### Cost function: time, not distance
`astar.py`'s edge cost is pure step distance (`1.0`/`√2`)
([astar.py:23-24](../ros2_ws/src/vto_planning/vto_planning/astar.py#L23-L24)).
Lattice primitives have different execution times (a pivot costs real time despite
zero displacement) — cost per primitive should be its **execution time** (plus a
fixed penalty on pivot-in-place primitives so the search only uses them when a turn
genuinely can't be done with an arc), since `time_to_goal` and smoothness — not raw
path length — are the metrics from doc 20 §3 this pipeline is meant to move.

### Output
Reconstruct the solution by concatenating each chosen primitive's dense `poses`
trace (denser than `astar.py`'s sparse `(row,col)` list — arcs need enough points
that Pure Pursuit doesn't cut them, echoing doc 10's corner-cutting lesson). Bonus,
not required: `astar_planner_node.py`'s `_publish_path` currently hardcodes
`orientation.w = 1.0` for every pose
([astar_planner_node.py:158](../ros2_ws/src/vto_planning/vto_planning/astar_planner_node.py#L158))
— since lattice tracks heading natively, the lattice node can fill in the real
per-pose orientation instead, though nothing downstream currently consumes it.

### Complexity
State space grows from `|cells|` to `|cells| × 16` headings, but branching factor
per expansion shrinks (~5-7 primitives vs. 8 fixed moves) — still standard A\*,
`O(b^d)`-ish bounded by the heuristic. The existing octile heuristic
([astar.py:34-40](../ros2_ws/src/vto_planning/vto_planning/astar.py#L34-L40)) stays
**admissible** when applied to just the `(x,y)` part of the extended state (it
ignores heading-change cost, which is `≥ 0`, so it never overestimates) — no need
for a fancier heuristic to keep correctness, though a tighter one would search
fewer nodes.

## Interview angle

- **Q: If diff-drive can pivot in place, what does a lattice actually buy you?**
  Not feasibility (an 8-connected path is always drivable via pivot+drive) —
  **path quality**: fewer stop-and-pivot events, lower curvature, less
  curvature-triggered slowdown downstream. Contrast with a car-like robot, where
  lattice/Hybrid A\* is about feasibility, not just quality.
- **Q: How do primitives generated at heading 0 get reused at every other heading
  and cell?** Rotational + translational invariance of the motion model — a
  primitive executed from any pose is the same shape, just rotated/translated, so
  it's generated once and looked up, not recomputed per search node.
- **Q: Why does primitive collision-checking differ from grid A\*'s?** Grid A\*
  only has to check the destination cell (moves are straight cell-to-cell hops); a
  curved primitive can clip an obstacle mid-arc without either endpoint touching
  it, so every sampled pose along the primitive must be checked.
- **Q: Why cost primitives by time instead of distance?** The metrics this
  pipeline is meant to move (`time_to_goal`, angular-rate smoothness) are about
  execution, not geometric length — a distance-only cost would let the search
  prefer a short path full of expensive pivots over a slightly longer smooth one.
- **Q: Does adding heading to the state break A\*'s optimality guarantee?** No,
  as long as the heuristic used stays admissible on the extended state — using the
  existing position-only octile heuristic (which ignores the non-negative
  heading-change cost) keeps it admissible, just less informed than an ideal one.
